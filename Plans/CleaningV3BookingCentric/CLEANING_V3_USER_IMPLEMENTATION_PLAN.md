## Shared product contract (applies to all four plans)

**Status:** proposed implementation handoff, not implemented or runtime-verified. Scope: simplify the existing Cleaning V3; no V4, new scheduling product, new workflow engine, payment gateway, or unrelated redesign. User-approved direction: each day generated by recurring cleaning is its own booking, with its own number, date, cost, team, supervisor (where required), state, cancellation and history. Recurrence is a creation-time convenience only. Do not show visit/session/series management for normal recurring cleaning. One-off cleaning uses the same experience. Genuine multi-day event assistance and historical multi-session bookings are a compatibility boundary, not permission to silently split or delete them. Keep existing internal execution/session identity wherever required for financial and operational controls. Existing daily booking behavior is the target, not a return to legacy V2 pricing.

**Shared invariants:** I-01 independent booking IDs and scoped mutations; I-02 quote acceptance is atomic/idempotent, exact allocation conserves all components and discounts; I-03 server is the only authority for status, actions, attendance, clock and money; I-04 one actor cannot access another customer's, worker's or supervisor's data; preserve pre-travel location privacy, authorization and existing dispatch admission/funding gates; I-05 completion never implies cash receipt or settlement; preserve actual evidence, segregation of duties, ledger reconciliation, equipment custody and deposit protections; I-06 terminal jobs cannot start, search, pause or mutate other jobs; I-07 no money decimals or raw currency codes in Arabic presentation; format e.g. 365,000 ل.س and 2 hours 30 minutes as ساعتان و30 دقيقة. Do not round away real payable fractions: obtain a documented integer-SYP allocation/rounding policy if any authoritative amount is fractional. Keep exact internal accounting, never use floating point for financial decisions. I-08 preserve genuine event/legacy compatibility and existing scope boundaries; I-09 no duplicated actions/notifications or optimistic false success.

**Shared delivery order:** B0 baseline and decision checks -> B1 identity/quote + B2 financial relationships -> B3 lifecycle/API projection and B4 role scoping -> contract freeze G1 -> independent mobile U/W/S implementation and B5 Filament work (parallel where nonconflicting) -> B6/B7 cross-app verification and release gate G2. UI agents may build local typed fixture tests before G1, but must not invent or hard-code a competing wire contract. Backend owns the canonical API and role-specific actions; mobile agents own their repositories only. All four plans use the same work package IDs and cross-plan references.

**Required execution discipline:** start in C:\laragon\www\Dllni; read local AGENTS.md/active project instructions and current plan; inspect git status/diff and active routes; capture baseline failures separately. As of 2026-11-26 Rider reported all four repos on dev with pre-existing dirty work (backend 178 entries, customer 23, worker 12, supervisor 19; snapshot only, refresh before implementation). Never stash/reset/checkout over unrelated edits; coordinate changes in overlapping files. No production data deletion, blanket migration:fresh, global feature-flag relaxation, fabricated payment evidence, or bypass of approvals. Only explicitly verified disposable QA databases may be reseeded. Work through checklist items, recording actual commands, exit codes, screenshots/API/DB evidence, failures and blockers. A passing static check is not an emulator or browser pass. No test is considered passed until executed.

**Common UI requirements:** existing application design system, Arabic-first RTL, correct back navigation, consistent spacing and typography, one clear primary action appropriate to state, secondary actions only when useful; no internal database IDs, contract-version labels, repeated explanatory cards, or permanent refresh controls. Manual retry only for stale/error state; automatically reconcile on foreground/realtime where existing infrastructure allows. Clock is a server-backed elapsed work time presentation: hidden before start and on cancelled; visible running/paused, pending pause does not stop billing, completed becomes static actual duration; no device-authoritative time or invented planned-time completion. Use compact numeric LTR digits inside RTL layout. Accessibility: screen-reader state/action labels, sufficient touch target, narrow-width/large text wrapping, no color-only states. Foundry Product UI was requested; Foundry runtime tools were not exposed during plan creation. These are UI implementation specifications, not rendered or approved Foundry scenes. At execution, if available, load foundry_context and compose existing design-system screens, render/review actual pixels; otherwise use existing Flutter/Filament components and capture real emulator/browser screenshots. Do not block safe contract work on absent Foundry.

**Open consequential decisions / stop conditions:** D-01 user explicitly requires independent recurring bookings. Proposed internal one execution record per new daily booking and shared quote links; validate feasibility and retain session IDs. D-02 historical or active multi-visit V3 data must remain read-compatible; if conversion is required, present non-destructive mapping/reconciliation and obtain explicit decision before migrating live data. D-03 preserve existing genuinely multi-day event assistance, unless user approves different semantics. D-04 integer SYP display is required; if any actual amounts contain subunits, reconcile and obtain approval for allocation/rounding before changing stored/priced money. D-05 retain current admission, funding, custody and cash verification policies; changing which steps require approval or who controls work is a separate product/security decision. Stop only the affected work package on unresolved pivotal decisions; continue independent safe slices.

Record files changed, tests added/updated, actual evidence, known deviations, rollback conditions, unresolved risks and next owner. Do not report success from implementation alone.

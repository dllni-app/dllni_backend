# Cleaning V3 — Architecture, Service Reuse and Duplication Audit

**Date:** 2026-11-27 | **Status:** Static source audit; corrections NOT implemented; commercial release NOT approved  
**Scope:** Dllni_backend (including Filament), dllni-user-app, dllni_cleaning_owner_app (active and Worker V2 presentation), dllni_supervisor_app.  
**Method:** Module Engineering continuation/hardening review via Rider. Current dirty working tree is the authority; plans and prior ledgers are secondary evidence. No acceptance scenarios, application source modifications, data writes, migrations, deployments, or flag changes. Only this audit is authorized to be written.

## 1. Executive assessment

**Retain the booking-centric architecture. Consolidate the integration, not the signed commercial safeguards.**

The current implementation is neither wholly duplicated nor wholly shared. Independent V3 non-event dates are already represented by separate existing CleaningBooking rows with a single internal execution session each; event assistance and historical multi-session orders intentionally retain a different representation. A session ID is a technical execution/assignment scope, not another customer-visible booking. The quote-to-booking relationship preserves the original signed agreement across dates. New V3 catalog versioning, quote signature verification, exact scope, active work intervals, consent revisions, independent verification and cash evidence are justified responsibilities. They are not reasons to create new deposits, workers, bookings, penalties, coupons, inventory or operational engines.

The existing system already defines cancellation fee configuration for both actors, worker debt/deposit mechanics, administrative penalty reversal, worker trust consequences, commission settings, supervisor hourly rates, supervisor assignment, equipment custody, and most execution transitions. DEC-01 must be narrowed to the few unresolved **application and reconciliation** semantics, not treated as permission to design a new financial system.

Highest priority finding: shared session cancellation still exposes a mutation path with weaker V3 financial admission/reconciliation checks than the V3 booking cancel path. Do not unblock all cancellation blindly. First ensure the same decision and financial consequences are enforced under the same booking/execution transaction from every entry point. Existing policy should be consumed directly when eligible.

Other source-confirmed integration gaps: a separate worker daily-earnings endpoint and screen coexist with an older parent-assignment transaction view; the general financial report omits verified supervisor company receipts and session-based revenue in its legacy totals; legacy and new settlement paths have different semantics requiring deliberate reconciliation, not destructive merging. Several V3 helpers overlap existing service responsibilities; consolidation candidates must be proved equivalent, not deleted by prefix.

### 4.1 What DEC-01 should now mean

**Remove from business-decision backlog:** cancellation fee amount source, worker cancellation monetary penalty mechanism, worker trust penalty, deposits/debt/allowance/settlement, manual penalty review/reversal, basic commission source, existing supervisor hourly and eligible fixed-per-visit compensation configuration, platform coupon redemption/reversal machinery, equipment custody and funding reservation ownership. These are existing rules or code paths, even where further integration and tests are required.

**Implementation blockers rather than decisions:** reconcile cancellation entry points under lock, source-qualified penalty identity, choose existing service for fee-free vs accepted cancellation, release/reconcile exact resources, source-qualified earnings projection, unified admin reports, historical/compatibility test evidence. Do not request the user redefine policy to close these tasks.

**Only conditional decision candidates if source tracing confirms absence:** customer cash refund/compensation after partial payment/work (recipient, authorization and accounting); allocation/release of externally verified funding and group-discount eligibility after one cancelled child where signed contract does not already specify it; actual financial liability for lost/damaged equipment or unresolved exceptional settlement; manual supervisor partial-day/replacement/cancellation liability if the signed basis does not specify it. No numeric policy is proposed. Source evidence above demonstrates custody, debt, and partial fee-refund primitives; it does not prove a full policy for every combination. Preserve fail-closed boundaries until the exact exception is specified and verified.

## 10. Historical compatibility and regression risks

- Independent daily booking means independent customer lifecycle, while event assistance retains grouped execution, historical V2/older bookings retain their contracts. Do not convert historical parent/child data or reinterpret booking/session IDs.
- Keep source-qualified assignment ID across customer, worker, supervisor, deep links, disputes and earnings. Do not infer one sibling as another when a projection is absent or revoked. Exact worker/role privacy is part of the contract.
- An agreed price remains distinct from assessed cancellation fee, unpaid amount, posted cash and company receipt. No silent repricing after a setting changes; no float recomputation of signed cents, no loss of original signature/quote revision.

- Do not remove signed quote verification, funding credit limits, actor separation, cash reference uniqueness, independently verified supervisor attendance, active roster checks, and one-open interval/one-pending request constraints.

- Worker V2 remains dormant; no startup routing, new architecture activation, package transplant or rebuild to satisfy a work package.

# Supervisor-led group bookings: remaining operational integration

## Implemented pricing and persisted data

`cleaning_financial_settings.supervisor_hourly_rate` controls the supervisor's hourly charge. `CleaningSupervisorHourlyPricing` calculates one fee for concurrent worker schedules: the union of covered intervals, rounded to billable minutes. The estimate adds this fee before commission and the minimum-order calculation. Approved room-period and V2 quotes hash the supervisor fee into the signed pricing snapshot. Bookings store `property_details._supervisor_pricing = {hourlyRate, billableMinutes, hours, fee}`; worker team allocations exclude this fee from the cleaning workers' distributable subtotal.

The same catalog price source applies to regular/deep room modes: `cleaning_room_types.regular_hourly_rate`, `.deep_hourly_rate` and editable `suggested_minutes_by_size`. The customer can override each room with `propertyDetails.room_estimated_hours["bedroom.small.1"]`, V2 `rooms[].estimatedHours`, or room-period `roomPeriods[].estimatedHours`; all inputs denote **work hours for that room**, not division by worker count.

## P0: operational supervisor lifecycle for other group contracts

**Do not describe V2 or room-period multi-worker bookings as operationally supervisor-led yet.** Those flows still create `booking_kind = standard`, even though they now include the supervisor fee and a persisted snapshot. The supervisor start/verification/handover/finish workflow operates on a single legacy `supervised_team` booking. Simply changing the booking kind for V2 would bypass `syncRooms` and fail room linking and session-specific execution. Until the lifecycle integration is completed, the product must distinguish billed supervision and *read-only visit visibility* from operational supervisor execution.

### Implemented safe V2 supervisor visibility (2026-10-17)

- An active `Cleaning Supervisor` may read their assigned standard, multi-worker, supervisor-priced V2/room-period bookings via `GET /api/v1/supervisor/v2/bookings`, `GET /api/v1/supervisor/v2/bookings/{booking}`, and `GET /api/v1/supervisor/v2/bookings/{booking}/visits/{sequence}`. Queries require an **active assignment to the authenticated supervisor**, and never return customer identity, phone, address, notes, billing or private evidence. Legacy `GET /api/v1/supervisor/bookings/{booking}` still serves only `supervised_team`.
- Active `Cleaning Ops Manager`/`Super Admin` may assign/reassign one supervisor for **visibility across all scheduled visits** using `POST /api/v1/admin/cleaning/supervisor-v2-bookings/{booking}/supervisor` with `supervisorUserId` (and `reason` for reassignment). Both API and Filament now call `CleaningSupervisorAssignmentService`, preserving one active assignment row, supervisor principal locking, all-visit overlap checks, custody safeguards, 10–500-character reassignment reason, and assignment/reassignment audit activity. This assignment is **booking-level**, not one row per visit; it does not initialize a supervisor session execution state machine. The API preserves its original role restrictions and does **not** authorize generic `admin` callers.
- The Filament booking detail page `ViewCleaningBooking` now has the Arabic **"إسناد المشرف / تغييره"** header action on eligible active legacy `supervised_team` or multi-worker standard V2/room-period schedules with a frozen `_supervisor_pricing` snapshot. Only active `admin`, `Super Admin` and `Cleaning Ops Manager` staff can perform it (Ops Managers also need `bookings.update`); `Customer Support` cannot, even if granted `bookings.update`. The form lists **active Cleaning Supervisor** accounts, preselects the current assignment and requires a recorded reason when transferring to a different supervisor. It rechecks privileges and all scheduling/custody conditions during the transaction and displays rejection feedback without partial assignment changes. This does **not** authorize supervisor start/finish actions in V2.
- For time-period V2, each read-only visit exposes the persisted `cleaning_booking_sessions` status, scheduled room tasks and **session-specific** accepted/arrived counts; per-room task completion is explicitly `not_tracked_per_room`. Room-period contracts have no session records yet: visits are grouped by `visit_sequence`, but their attendance source is `unavailable` with null counts/readiness. This avoids inferring attendance from booking-level workers.
- `POST /api/v1/supervisor/v2/bookings/{booking}/visits/{sequence}/{action}` for the documented execution actions, and old booking-level supervisor **execution** mutations attempted on actively assigned standard V2, return `422 SUPERVISOR_V2_EXECUTION_UNAVAILABLE`; other supervisors receive 404. Existing authorized inventory custody endpoints, including `POST /api/v1/supervisor/bookings/{booking}/materials/receive`, are deliberately **excluded** from this transition guard. Legacy `supervised_team` execution is unchanged. Standard session lifecycle remains owned by existing worker/customer routes and is **not** converted to a supervised session workflow.
- Group inventory custody already considers standard multi-worker bookings with active supervisor assignments: inventory read, material kit receipt, equipment acknowledgments and returns are exposed through their separately authorized inventory endpoints. These remain **booking-wide**, not reconciled per visit. Reassigning a V2 supervisor is refused after material receipt or while supervisor equipment remains unreturned. An assignment does not itself issue material/equipment, and this capability does **not** imply a complete per-visit supervisor execution lifecycle.

Before shipping all group types as supervisor-operated:

1. Add session-aware supervised-team initialization for each V2 visit and room-period schedule in `SupervisedTeamScheduleService` and `CleaningTimePeriodBookingService` / `RoomPeriodBookingCreationService`, mapping `cleaning_booking_room_id`, schedule key and visit sequence to an active per-session supervisor and trustworthy execution ledger. Current booking-level assignment only grants visibility/custody access; room-period contract still does not create sessions.
2. Adapt `SupervisorWorkflowController`, `SupervisedTeamService` and worker lifecycle middleware to accept the active session and protect start/travel/room-complete/finish state consistently across concurrent workers, visits and dates. A supervised worker must never invoke the legacy worker-owned start/complete API.
3. Reconcile supervisor and worker attendance, SOS, substitutions and payroll separately. Use the frozen `_supervisor_pricing` fee in reporting and preserve group customer quote totals; worker distributions must exclude supervisor compensation.
4. Handle recurring-hours and open-time bookings with multiple workers explicitly. Their duration/extension/metering lifecycle currently needs per-visit supervisor billing and final remeasurement. Either implement the same session-aware workflow and fee adjustments or reject unsupported multi-worker modes through user-facing 422 validation. Do not silently offer standard worker-controlled execution under a "supervised" label.
5. The customer Flutter app now loads active Filament room types from the public `GET /api/v1/cleaning/suite-config` `data.roomTypes` payload, with `GET /api/v1/user/cleaning/room-types` still available to authenticated customers. A real Android guest flow displayed the extra `toilet` code (مرحاض) and successfully created a two-worker booking with that room; backend persistence, price and session were verified. Finish post-rebuild Arabic review-label verification, editable-history and worker task display as separate acceptance tests.

Existing legacy single-date `serviceType=supervised_team` bookings continue to use their supervisor workflow. Pricing and snapshot regressions are covered by `CleaningRoomHourlyPricingTest`, `CleaningTimePeriodV2Test` and `CleaningRoomPeriodContractPhase1Test`. `SupervisorScheduledV2ReadOnlyTest` covers permissions, active ownership, per-visit read models, unavailable room-period attendance, 422 execution guards, cross-visit scheduling conflicts and assignment safety. `CleaningBookingSupervisorAssignmentActionTest` covers the Filament action, privileged role/permission checks, legacy/V2 eligibility, visit overlap, material/equipment custody, reason and activity audit. Implementation of item 1–4 still requires dedicated **mutating API lifecycle** tests before exposing supervisor start/finish actions.

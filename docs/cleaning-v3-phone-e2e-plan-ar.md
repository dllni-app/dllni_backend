# ع الندهة — خطة الاختبار الشامل على الهاتف بعد إكمال محرك التنظيف V3

تاريخ إعداد الخطة: 24 نوفمبر 2026. الحالة: خطة تنفيذ لاحقة، لم يبدأ اختبار الهاتف.
المرجع: ALNADHA_DYNAMIC_CLEANING_FINAL_AR_WORKFLOW_PLAN، 21 نوفمبر 2026، مع تأجيل اختبار الهاتف بطلب صاحب المشروع إلى نهاية البرمجة.

## 1. النطاق وشروط بدء الاختبار

- المستودعات الأصلية: dllni_backend (Laravel + Filament)، dllni-user-app، dllni_cleaning_owner_app، dllni_supervisor. فرع dev فقط؛ لا Worktrees أو فروع إضافية، ولا تعديل main.
- الهاتف الفعلي المتصل Redmi Note 10 Pro. لا محاكي. لا يبدأ تثبيت APK أو استخدام ADB في مرحلة البرمجة الحالية.
- قبل أول تثبيت: اكتمال نواقص الكود، فحص جميع SHA وحالة Git، نشر الباك إند dev، التأكد من أن جميع التطبيقات تستخدم API dev نفسه، فحص MySQL المحلي/الاختباري والهجرات والجداول الفعلية، Queue وScheduler وRealtime وFCM.
- اعتماد كتالوج تجريبي واضح الأسعار والجهد ونطاقات البنود، إثبات مصدر تمويل مستقل ومتحقق منه قبل أي اختبار مالي إيجابي، واختبار سباقات MySQL. لا تكفي نتيجة SQLite لإثبات أقفال المعاملات.
- تشغيل أمر cleaning:v3-readiness ومراجعة جميع الموانع. التقرير الحالي متعمد أن يرفض الجاهزية التجارية حتى استكمال التنفيذ والأدلة؛ لا يُعدّل التقرير لمجرد الحصول على PASS.
- تبقى مسارات إنشاء العرض والحجز التجاري مقفلة إلى حين استيفاء الشروط. قبل ذلك يمكن اختبار المعاينات والحالات المرفوضة فقط؛ لا تستخدم أموالاً أو حجوزات إنتاجية، ولا تحاكي إثبات تمويل تجاري حقيقي عبر تغيير يدوي للحالة.
- توفير حسابات dev للعميل وعاملين على الأقل (ويفضل ثلاثة فأكثر) ومشرف وإدارة، وعناوين ضمن وخارج المنطقة، ومواعيد متاحة، وطلبات V2 تاريخية وطلب V3 غير مكتمل إن كان إنشاؤه المصرح به متاحاً.
- استخدام حسابات الاختبار القائمة دون حفظ كلمات المرور في المستودع أو السجلات أو لقطات الشاشة. يمكن تبديل الحسابات على الهاتف نفسه، أو استخدام حزم QA مستقلة لكل دور/عامل إذا توفرت دون تغيير هوية حزمة الإنتاج. اختبار السباقات الفعلية عبر API/MySQL قبل الاختبار الهاتفي، لا الادعاء بإثبات التزامن من تبديل حسابات متتابع على هاتف واحد.

## 2. تحضير الأدلة

أنشئ مجلد QA/cleaning_v3_phone_e2e_<run-date>/ على اللابتوب، ومجلدات backend, admin, customer, worker, supervisor, cross_app, regressions.
سجل SHA لكل مستودع ونسخة APK ووقت الاختبار ونسخة Android وعنوان API dev دون أسرار.
لكل حالة سجل: ID، المتطلبات السابقة، حساب QA باسم مستعار، رقم Booking/Session/occurrenceKey، الخطوات، المتوقع، الفعلي، حالة PASS/FAIL/BLOCKED/NOT RUN، صور قبل/بعد، فيديو عند الحاجة، logs وAPI منزوع الحساسية، نتائج الاستعلامات المالية/التشغيلية. لا تلتقط عناوين أو رموز تحقق أو بيانات أشخاص حقيقيين.

## 4. آلية التنفيذ

أولاً: بيئة dev والكتالوج واختبارات الرجوع إلى V2. ثانياً: المعاينة والجدولة والقدرة. ثالثاً: العروض والحجز فقط بعد استيفاء التمويل. رابعاً: البحث والخصوصية وحالات العامل والمشرف. خامساً: العمل والعداد والتوقف والإكمال. سادساً: الدورية والفوترة والامتثال والإشعارات. سابعاً: التحديث والتراجع وإعادة الاختبار.
لا تنتقل من خلل P0 (خطأ أموال، تسرب موقع، فقد طلب، Crash يمنع المسار، تكرار حجز) إلى الاعتماد النهائي. وثّق السبب، أصلح على dev، أعد اختبار الحالة وجميع الحالات المتأثرة. عند توقف مسار بسبب بوابة التمويل، سجله BLOCKED مع المتطلب؛ لا تتجاوزه ولا تضع PASS.
اختبار الـ6 ساعات يمكن تسريعه في dev ببيانات fixture معزولة وتوقيت خادم موثق، لا بتغيير ساعة الهاتف أو منطق الإنتاج. اختبارات التزامن والصفوف المالية تتم على MySQL متصل بالاختبار مع نتائج مستقلة، حتى لو جرى تشغيل واجهات التطبيقات على هاتف واحد.

## 5. معايير النجاح النهائية

- نجاح كل P0 وP1 وعدم وجود BLOCKED في متطلبات الإطلاق، مع إثبات عدم تغيير بيانات V2.
- إكمال دورة فعلية من Filament إلى العميل إلى العامل/المشرف إلى الإيصال والتقييم، وطلبات دورية ومجموعة ومساعدة ساعية.
- اختبار حقيقي على الهاتف لكل APK وتوثيق نتيجة لكل حالة، إعادة اختبار بعد آخر Commit.
- لا نشر main أو إنتاج دون اعتماد صاحب المشروع.
- الحالة الحالية: المعاينات ليست حجزاً، وتفعيل إصدار عروض الأسعار وإنشاء الحجوزات والتسوية الحقيقية ما زال مشروطاً بإكمال التنفيذ وإثبات التمويل والتعرفة. الخطة لا تدّعي أن جميع البرمجة منتهية.
